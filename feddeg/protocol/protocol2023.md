## 1. Введение

В настоящем документе приведено описание порядка взаимодействия логических элементов системы дистанционного электронного голосования, называемого далее протоколом ДЭГ. В разделе 2 описаны криптографические механизмы, которые используются в протоколе, в разделе 3 перечислены логические участники взаимодействия, в разделе 4 описаны шаги выполнения протокола, формирующие порядок взаимодействия участников.

## 2. Базовые криптографические механизмы

В настоящем разделе описаны криптографические механизмы, используемые в протоколе ДЭГ.

Обозначим:

- 𝐻 — хэш-функция Стрибог с длиной выхода 256 битов, определенная в стандарте ГОСТ Р 34.11–2012 [2];
- 𝐻𝑀𝐴𝐶 — функция HMAC_GOSTR3411_2012_256 с длиной ключа 256 бит, определенная в Рекомендациях по стандартизации Р 50.1.113–2016 [3];
- ∥ — конкатенация двоичных строк;
- 𝑎[𝑖; 𝑗] = (𝑎ᵢ, …, 𝑎ⱼ) — подстрока байтовой строки 𝑎 = (𝑎₀, …, 𝑎ₜ₋₁);
- strₜ(𝑟) — функция, преобразующая целое число 𝑟 = 256ᵗ⁻¹𝑏ₜ₋₁ + 256ᵗ⁻²𝑏ₜ₋₂ + ⋯ + 256𝑏₁ + 𝑏₀, 𝑏ᵢ ∈ {0, …, 255}, 𝑖 = 0, …, 𝑡 − 1, в байтовую строку 𝑏₀ ∥ … ∥ 𝑏ₜ₋₁;
- STRₜ(𝑟) — функция, преобразующая целое число 𝑟 = 256ᵗ⁻¹𝑏ₜ₋₁ + 256ᵗ⁻²𝑏ₜ₋₂ + ⋯ + 256𝑏₁ + 𝑏₀, 𝑏ᵢ ∈ {0, …, 255}, 𝑖 = 0, …, 𝑡 − 1, в байтовую строку 𝑏ₜ₋₁ ∥ … ∥ 𝑏₀;
- int(𝑏) — функция, преобразующая байтовую строку 𝑏 = 𝑏₀ ∥ … ∥ 𝑏ₜ₋₁ в целое число 𝑟 = 256ᵗ⁻¹𝑏ₜ₋₁ + 256ᵗ⁻²𝑏ₜ₋₂ + ⋯ + 256𝑏₁ + 𝑏₀;
- 𝑥 ← 𝑋 (𝒰) — элемент 𝑥 выбирается из множества 𝑋 случайно в соответствии с равномерным распределением;
- {0, 1}ⁿ — множество всех 𝑛-битовых строк, где 𝑛 — натуральное число;
- {0, 1}∗ — множество всех битовых строк конечной длины, включая пустую строку;
- ⊥ — символ, обозначающий событие «ошибка»;
- 𝑥 mod 𝑦 — остаток от деления целого числа 𝑥 на целое число 𝑦;
- ⊕ — операция покомпонентного сложения по модулю 2 двух битовых строк одинаковой длины;
- ℰ — эллиптическая кривая id-tc26-gost-3410-2012-256-paramSetB, параметры которой определены в Рекомендациях по стандартизации Р 1323565.1.024–2019 [4];
- 𝑞 — простое число, порядок группы точек эллиптической кривой ℰ;
- 𝑃 — образующий элемент группы точек эллиптической кривой ℰ;
- 𝒪 — нейтральный элемент группы точек эллиптической кривой ℰ;
- ℤ𝑞 — конечное поле порядка 𝑞, где 𝑞 — простое;
- ℤ∗𝑞 — мультипликативная группа конечного поля ℤ𝑞.

Всюду далее открытые ключи (ключи шифрования, ключ проверки подписи) являются элементами группы точек эллиптической кривой ℰ, закрытые ключи (ключи расшифрования, ключ подписи) являются элементами мультипликативной группы конечного поля ℤ∗𝑞.

Все элементы конечного поля ℤ𝑞, передаваемые и используемые в рамках протоколов, описанных в настоящем документе, представляются в виде байтовых строк в формате little-endian длины 32 байта. Все точки с координатами (𝑥, 𝑦) эллиптической кривой, передаваемые и используемые в рамках протоколов, описанных в настоящем документе, представляются в виде байтовой строки 𝑏ₓ ∥ 𝑏ᵧ, где 𝑏ₓ и 𝑏ᵧ — байтовое представление 𝑥-координаты и 𝑦-координаты точки соответственно в формате little-endian, длины 32 байта.

### 2.1. Хэш-функция

Хэш-функция, отображающая двоичные строки конечной длины в элементы конечного поля ℤ𝑞, определяется функцией 𝐻𝑎𝑠ℎ.

**Вход:**

- сообщение 𝑚 ∈ {0, 1}∗;
- идентификатор области применения 𝐷𝑆𝑇 длины 𝑙 байт.

**Выход:**

- хэш-значение ℎ ∈ ℤ𝑞.

### 2.2. Схема подписи

Схема подписи 𝑆 определяется следующими процессами (используется схема, определенная стандартом ГОСТ Р 34.10-2012 [1]).

**Генерация ключей 𝑆. `KeyGen`**

**Выход:**

- ключ подписи 𝑠𝑘;
- ключ проверки подписи 𝑝𝑘.

**Формирование подписи 𝑆. `Sign`**

**Вход:**

- ключ подписи 𝑠𝑘;
- сообщение 𝑚.

**Выход:**

- подпись 𝜎.

**Проверка подписи 𝑆. `Verify`**

**Вход:**

- ключ проверки подписи 𝑝𝑘;
- сообщение 𝑚;
- подпись 𝜎.

**Выход:**

- бит 𝑏 ∈ {0, 1}: 𝑏 = 1 (𝑏 = 0) — проверка завершилась (не)успешно.

### 2.3. Схема подписи вслепую

Обозначим: `Hash_blind(m) = Hash(m, DST_blind)`, где:

`DST_blind = BlindSign-TeZhu-V00-H2F:id-tc26-gost-3410-2012-256-paramSetB_Streebog-256_XMD_RO`.

Схема подписи вслепую 𝐵𝑆 определяется следующими процессами (используется схема, определенная в работе [9]).

**Генерация ключей 𝐵𝑆. `KeyGen`**

**Выход:**

- ключ подписи 𝑠𝑘;
- ключ проверки подписи 𝑝𝑘.

![Алгоритм `BS.KeyGen()`; исходная растровая формула из PDF, стр. 7](protocol2023-assets/01-signature-keygen.png)

**Формирование подписи вслепую** ⟨𝐵𝑆.`Sign`(𝑠𝑘, 𝑝𝑘), 𝐵𝑆.`User`(𝑝𝑘, 𝑚)⟩

**Вход функции `Sign`:**

- ключ подписи 𝑠𝑘;

**Вход:**

- ключ проверки подписи 𝑝𝑘;

- значение подписи 𝜎.

**Выход:**

- бит 𝑏 ∈ {0, 1}: 𝑏 = 1 (𝑏 = 0) — проверка завершилась (не)успешно.

### 2.5. Схема разделения секрета (с доверенным дилером)

Схема разделения секрета позволяет разделить секрет 𝑠 между 𝑛 участниками таким образом, что любые 𝑘 участников, объединившись, могут восстановить секрет. Схема разделения секрета 𝑆𝑆 определяется следующими процессами (используется схема, определенная в работе [9]).

#### Разделение секрета 𝑆𝑆. `Share`

**Вход:**

- секрет 𝑠;
- общее число участников 𝑛 ∈ ℕ;
- пороговое число участников 𝑘 ∈ ℕ, 𝑘 ≤ 𝑛.

**Выход:**

- доли (𝑠₁, …, 𝑠ₙ).

![Алгоритм `Share(s, n, k)`; исходная растровая формула из PDF, стр. 13](protocol2023-assets/16-secret-share.png)

#### Восстановление секрета 𝑆𝑆. `Comb`

**Вход:**

- множество номеров {𝑖₁, …, 𝑖ₖ} ⊆ {1, …, 𝑛};
- доли (𝑠ᵢ₁, …, 𝑠ᵢₖ).

**Выход:**

- секрет 𝑠.

![Алгоритм `Comb({i₁, …, iₖ}, {sᵢ₁, …, sᵢₖ})`; исходная растровая формула из PDF, стр. 14](protocol2023-assets/17-secret-combine.png)

- значение коммитмента `com`.

**Выход:**

- бит 𝑏 ∈ {0, 1}: 𝑏 = 1 (𝑏 = 0) — проверка завершилась (не)успешно.

## 3. Участники протокола

В настоящем подразделе кратко перечислены основные участники протокола ДЭГ и их функции.

- **Избиратель** — участник, являющийся гражданином, обладающим активным избирательным правом и включенным в списки избирателей.
- **Организатор** — участник, осуществляющий организацию процесса голосования (в том числе соответствующая избирательная комиссия).
- **Аутентификатор** — участник, осуществляющий идентификацию и аутентификацию избирателей (с помощью ЕСИА).
- **Регистратор** — участник, предоставляющий избирателям право получения бюллетеня (путем формирования подписи вслепую).
- **Урна** — участник, выдающий избирателям бюллетени и принимающий обратно заполненные зашифрованные бюллетени.
- **Учетчик** — участник, представляющий собой хранилище транзакций (бюллетеней избирателей и других данных), к которому есть постоянный доступ на запись и/или чтение у участников Урна, Организатор, Регистратор, Наблюдатель, а также осуществляющий подсчет итогов.
- **Наблюдатель** — участник, осуществляющий наблюдение за процессом голосования и аудит результатов голосования; имеет доступ к хранилищу транзакций, предоставляет публичный доступ ко всему содержимому данного хранилища через Портал наблюдения.

## 4. Этапы протокола

В настоящем подразделе описаны шаги выполнения протокола ДЭГ для 𝑛 независимых процедур голосования.

Будем считать, что взаимодействие между всеми участниками (в том числе с внешними участниками) осуществляется защищенным образом (обеспечивается аутентификация участников и конфиденциальность передаваемых данных), сообщения от Организатора, Регистратора и Учетчика, публикующих данные в Учетчике, аутентифицированы. При описании протокола не указываются особенности работы системы, с помощью которой он может быть реализован (например, способы аутентификации участников и пр.).

### 4.1. Формирование исходных данных

#### 4.1.1. Формирование списков избирателей

1. Избиратель с помощью Единого портала государственных услуг подает заявление на участие в ДЭГ (заявление включает идентификатор СНИЛС и номер паспорта `passport` Избирателя).
2. На основании заявлений избирателей Центральная избирательная комиссия (ЦИК) для каждого 𝑖 ∈ {1, …, 𝑛} формирует списки избирателей, участвующих в ДЭГ.
3. Организатор генерирует в системе ключ для схемы коммитмента 𝐾 = 𝐶.`KeyGen()`.

#### 4.1.2. Передача данных голосования

1. ЦИК передает Организатору данные голосования для каждого 𝑖 ∈ {1, …, 𝑛}, в том числе списки избирателей.

### 4.2. Инициализация системы

#### 4.2.1. Генерация ключей

1. Организатор генерирует частичный (разделяемый) ключ шифрования:

   (𝑠𝑘дел, 𝑝𝑘дел) = 𝑆𝐸.`KeyGen()`.

   Закрытый ключ 𝑠𝑘дел разделяется по схеме разделения секрета с помощью функции 𝑆𝑆.`Share`(𝑠𝑘дел, 𝑁, 𝑘) между 𝑁 держателями долей ключа (с некоторым параметром 𝑘 ≤ 𝑁), вычисленные доли 𝑠ᵢ записываются на защищенные носители, которые отдаются держателям долей ключа. Ключ 𝑠𝑘дел уничтожается на устройстве.
2. Учетчик для каждого 𝑖 ∈ {1, …, 𝑛} генерирует частичный (неразделяемый) ключ шифрования:

   (𝑠𝑘неделⁱ, 𝑝𝑘неделⁱ) = 𝑆𝐸.`KeyGen()`.

3. Регистратор для каждого 𝑖 ∈ {1, …, 𝑛} генерирует ключ подписи вслепую:

   (𝑠𝑘blindⁱ, 𝑝𝑘blindⁱ) = 𝐵𝑆.`KeyGen()`.

#### 4.2.2. Загрузка данных голосования

1. Организатор передает Регистратору список избирателей.
2. Организатор передает Учетчику данные голосования для каждого 𝑖 ∈ {1, …, 𝑛}, содержащие:
   - идентификатор процедуры голосования (`VotingIDᵢ`);
   - хэш-значение от текста бюллетеня;
   - общее количество вариантов 𝑡ᵢ, максимальное и минимальное количество выбранных вариантов 𝑚ᵢₙᵢ, 𝑚ₐₓᵢ (1 ≤ 𝑚ᵢₙᵢ ≤ 𝑚ₐₓᵢ < 𝑡ᵢ).
3. Регистратор передает Учетчику ключи 𝑝𝑘blindⁱ, 𝑖 = 1, …, 𝑛.
4. Учетчик для каждого 𝑖 ∈ {1, …, 𝑛} публикует данные голосования совместно с соответствующими ключами 𝑝𝑘blindⁱ.
5. Организатор для каждого 𝑖 ∈ {1, …, 𝑛} формирует список значений коммитментов `comСНИЛС = C.Cmt(K, СНИЛС)` для избирателей из соответствующих списков и публикует список коммитментов в Учетчике.
6. Организатор передает Регистратору ключ 𝐾.
7. Организатор передает Урне текст бюллетеня, идентификатор `VotingIDᵢ` и ключ 𝑝𝑘blindⁱ проверки подписи вслепую для всех 𝑖 ∈ {1, …, 𝑛}.

#### 4.2.3. Загрузка ключа шифрования бюллетеней

1. Организатор передает Учетчику разделяемый ключ шифрования 𝑝𝑘дел.
2. Учетчик для каждого 𝑖 ∈ {1, …, 𝑛} формирует ключ шифрования бюллетеней:

   𝑝𝑘ᵢ = 𝑆𝐸.`KeyAgg`(𝑝𝑘дел, 𝑝𝑘неделⁱ).

3. Учетчик для каждого 𝑖 ∈ {1, …, 𝑛} публикует:
   - разделяемый ключ шифрования 𝑝𝑘дел;
   - неразделяемый ключ шифрования 𝑝𝑘неделⁱ;
   - итоговый ключ шифрования 𝑝𝑘ᵢ.
4. Учетчик передает Регистратору ключи 𝑝𝑘ᵢ, 𝑖 = 1, …, 𝑛.
5. Организатор через Портал наблюдения проверяет, что:
   - был опубликован известный ему разделяемый ключ шифрования 𝑝𝑘дел;
   - для каждого 𝑖 ∈ {1, …, 𝑛} итоговый ключ 𝑝𝑘ᵢ был правильно вычислен.

### 4.3. Предоставление права получения бюллетеня

#### 4.3.1. Идентификация и аутентификация избирателя

1. Избиратель обращается к Аутентификатору, который выполняет идентификацию и аутентификацию Избирателя с помощью ЕСИА, в результате чего Аутентификатор получает токен доступа, подписанный ЕСИА и содержащий информацию об Аутентификаторе (так называемый идентификатор клиента ЕСИА).
2. Аутентификатор передает Избирателю токен доступа.

#### 4.3.2. Получение подписи вслепую и ключа шифрования бюллетеней

1. Избиратель передает токен доступа Регистратору.
2. Регистратор проверяет корректность токена доступа, в том числе подпись ЕСИА и соответствие информации об Аутентификаторе.
3. Регистратор с помощью токена доступа получает из ЕСИА идентификатор СНИЛС и номер паспорта `passport` Избирателя.
4. Регистратор проверяет, что:
   - Избиратель есть в соответствующих списках избирателей;
   - Избиратель не получал бюллетень.

   Если какая-то из проверок завершена неуспешно, Регистратор возвращает Избирателю ошибку.
5. Регистратор передает Избирателю ключи 𝑝𝑘blindⁱ, 𝑖 = 1, …, 𝑛.
6. Избиратель генерирует ключи подписи (𝑠𝑘избⁱ, 𝑝𝑘избⁱ) = 𝑆.`KeyGen()`, 𝑖 = 1, …, 𝑛.
7. Избиратель и Регистратор для каждого 𝑖 ∈ {1, …, 𝑛} выполняют протокол формирования подписи вслепую ⟨𝐵𝑆.`Sign`(𝑠𝑘blindⁱ, 𝑝𝑘blindⁱ), 𝐵𝑆.`User`(𝑝𝑘blindⁱ, 𝑝𝑘избⁱ)⟩, в результате чего на стороне Избирателя формируется значение подписи 𝜎blindⁱ.
8. Регистратор передает Избирателю ключи шифрования бюллетеней 𝑝𝑘ᵢ, 𝑖 = 1, …, 𝑛, и соответствующие им идентификаторы голосования `VotingIDᵢ`.
9. Регистратор записывает в списке избирателей паспортные данные Избирателя, фиксируя тем самым факт выдачи подписи вслепую.
10. Регистратор формирует значение коммитмента `compass = C.Cmt(K, СНИЛС ∥ passport)` и для каждого 𝑖 ∈ {1, …, 𝑛} публикует его в Учетчике.

### 4.4. Подача заполненного бюллетеня

#### 4.4.1. Волеизъявление

1. Избиратель анонимно обращается к Урне и запрашивает текст бюллетеня по идентификатору `VotingIDᵢ` для каждого 𝑖 ∈ {1, …, 𝑛}.
2. Урна отправляет Избирателю текст бюллетеня для каждого 𝑖 ∈ {1, …, 𝑛}.
3. Избиратель для каждого 𝑖 ∈ {1, …, 𝑛} заполняет бюллетень, определяя набор (𝑚₁ⁱ, …, 𝑚ₜᵢⁱ), где значение 𝑚ⱼⁱ ∈ {0, 1} обозначает голос «за» (1) или «против» (0) за 𝑗-й вариант, 𝑗 = 1, …, 𝑡ᵢ, и зашифровывает его:

   ((𝑐₁ⁱ, …, 𝑐ₜᵢⁱ), 𝑑ⁱ) = 𝑆𝐸.`Enc`(𝑝𝑘ᵢ, (𝑚₁ⁱ, …, 𝑚ₜᵢⁱ), 𝑚ᵢₙᵢ, 𝑚ₐₓᵢ).

4. Избиратель для каждого 𝑖 ∈ {1, …, 𝑛} формирует транзакцию 𝑡𝑥ⁱ, включающую следующие данные:
   - идентификатор `VotingIDᵢ`;
   - зашифрованный бюллетень ((𝑐₁ⁱ, …, 𝑐ₜᵢⁱ), 𝑑ⁱ);
   - открытый ключ Избирателя 𝑝𝑘избⁱ;
   - значение подписи 𝜎blindⁱ.
5. Избиратель для каждого 𝑖 ∈ {1, …, 𝑛} подписывает транзакцию 𝑡𝑥ⁱ:

   𝜎ⁱ = 𝑆.`Sign`(𝑠𝑘избⁱ, 𝑡𝑥ⁱ).

6. Избиратель отправляет Урне подписанные транзакции (𝑡𝑥ⁱ, 𝜎ⁱ), 𝑖 = 1, …, 𝑛.
7. Урна проверяет для каждого 𝑖 ∈ {1, …, 𝑛}:
   - корректность формата транзакции (наличие необходимых полей, их длина и т. д.);
   - корректность подписи Регистратора в транзакции (с помощью функции 𝐵𝑆.`Verify`(𝑝𝑘blindⁱ, 𝑝𝑘избⁱ, 𝜎blindⁱ));
   - корректность подписи Избирателя под транзакцией (с помощью функции 𝑆.`Verify`(𝑝𝑘избⁱ, 𝑡𝑥ⁱ, 𝜎ⁱ));
   - уникальность ключа 𝑝𝑘избⁱ (по своей внутренней базе данных).

   Если какая-то из проверок завершена неуспешно, Урна возвращает Избирателю ошибку и не принимает бюллетень.

   В противном случае Урна:
   - добавляет ключ 𝑝𝑘избⁱ в свою внутреннюю базу данных;
   - отправляет транзакции Учетчику (не подписывая дополнительно);
   - формирует квитанцию о приеме транзакции (подписанная Урной принятая транзакция и ее идентификатор) и отображает ее Избирателю.

   На экране устройства избирателя отображается содержимое его транзакции и квитанции, которые избиратель может скопировать для дальнейшей проверки корректности учета.

#### 4.4.2. Публикация бюллетеня

Учетчик проверяет для каждого 𝑖 ∈ {1, …, 𝑛}:

- корректность формата транзакции (наличие необходимых полей, их длина и т. д.);
- корректность подписи Регистратора в транзакции (с помощью функции 𝐵𝑆.`Verify`(𝑝𝑘blindⁱ, 𝑝𝑘избⁱ, 𝜎blindⁱ));
- корректность подписи Избирателя под транзакцией (с помощью функции 𝑆.`Verify`(𝑝𝑘избⁱ, 𝑡𝑥ⁱ, 𝜎ⁱ));
- факт однократности транзакции с таким ключом Избирателя.

Если проверки пройдены, транзакции добавляются в Учетчик.

#### 4.4.3. Проверка бюллетеня

1. Избиратель с помощью Портала наблюдения проверяет (поиском по идентификатору транзакции из квитанции от Урны), что его транзакции находятся в хранилище. Если Избиратель не находит свои транзакции, то он обращается к Наблюдателю с жалобой, направляя ему свои транзакции и квитанции.
2. Если Наблюдатель получил жалобу, то он проверяет корректность транзакций (подписи Регистратора и Избирателя), квитанций (подпись Урны) и отсутствие в хранилище других транзакций с данным ключом. Если проверка завершилась успешно, Наблюдатель фиксирует факт некорректной работы системы.

### 4.5. Подведение итогов

#### 4.5.1. Прекращение выдачи и приема бюллетеней

1. По завершении голосования Регистратор прекращает выдачу подписей вслепую.
2. По истечении периода времени, предоставленного Избирателю для завершения голосования (в соответствии с параметром, установленным оператором, например — 15 минут), Организатор сообщает Урне и Учетчику о завершении приема бюллетеней.
3. Учетчик публикует транзакцию о завершении приема бюллетеней. После этого Учетчик не принимает бюллетени.

#### 4.5.2. Восстановление разделяемого ключа шифрования

1. Организатор проводит церемонию сборки разделяемого ключа расшифрования 𝑠𝑘дел с помощью функции 𝑆𝑆.`Comb`({𝑖₁, …, 𝑖ₖ}, {𝑠ᵢ₁, …, 𝑠ᵢₖ}). Для сборки ключа достаточно 𝑘 долей.
2. Организатор передает ключ 𝑠𝑘дел Учетчику.

#### 4.5.3. Подсчет итогов

1. Учетчик осуществляет проверку корректности шифрования для хранящихся бюллетеней с помощью функции:

   𝑆𝐸.`VerifyEnc`(𝑝𝑘ᵢ, (𝑐₁ⁱ, …, 𝑐ₜᵢⁱ), 𝑑ⁱ, 𝑚ᵢₙᵢ, 𝑚ₐₓᵢ).

2. Учетчик для каждого 𝑖 ∈ {1, …, 𝑛} осуществляет гомоморфное сложение шифртекстов (𝑐₁ⁱ, …, 𝑐ₜᵢⁱ), соответствующих успешно проверенным бюллетеням, с помощью функции 𝑆𝐸.`Add`, формируя тем самым итоговый шифртекст (𝑐̅₁ⁱ, …, 𝑐̅ₜᵢⁱ).

#### 4.5.4. Расшифрование итогов

1. Учетчик для каждого 𝑖 ∈ {1, …, 𝑛} осуществляет частичное расшифрование значения (𝑐̅₁ⁱ, …, 𝑐̅ₜᵢⁱ), используя части ключей:
   - вычисляет (μнеделⁱ, πнеделⁱ) = 𝑆𝐸.`DecPart`(`VotingIDᵢ`, 𝑠𝑘неделⁱ, 𝑝𝑘неделⁱ, (𝑐̅₁ⁱ, …, 𝑐̅ₜᵢⁱ));
   - проверяет значение (μнеделⁱ, πнеделⁱ) с помощью функции 𝑆𝐸.`VerifyDecPart`(`VotingIDᵢ`, 𝑝𝑘неделⁱ, (𝑐̅₁ⁱ, …, 𝑐̅ₜᵢⁱ), μнеделⁱ, πнеделⁱ);
   - вычисляет (μделⁱ, πделⁱ) = 𝑆𝐸.`DecPart`(`VotingIDᵢ`, 𝑠𝑘дел, 𝑝𝑘дел, (𝑐̅₁ⁱ, …, 𝑐̅ₜᵢⁱ));
   - проверяет значение (μделⁱ, πделⁱ) с помощью функции 𝑆𝐸.`VerifyDecPart`(`VotingIDᵢ`, 𝑝𝑘дел, (𝑐̅₁ⁱ, …, 𝑐̅ₜᵢⁱ), μделⁱ, πделⁱ).
2. Учетчик для каждого 𝑖 ∈ {1, …, 𝑛} публикует значения (μнеделⁱ, πнеделⁱ), (μделⁱ, πделⁱ).
3. Учетчик для каждого 𝑖 ∈ {1, …, 𝑛} осуществляет агрегирование результатов расшифрования, формируя результаты голосования:

   `resultᵢ = SE.DecAgg((𝑐̅₁ⁱ, …, 𝑐̅ₜᵢⁱ), μнеделⁱ, μделⁱ, pkнеделⁱ, pkдел)`.

4. Учетчик для каждого 𝑖 ∈ {1, …, 𝑛} публикует значения `resultᵢ`.

### 4.6. Аудит

Наблюдатель проверяет:

- количество бюллетеней, которые оказались в Учетчике, не превышает количества Избирателей, которым выдали подпись вслепую (с учетом 𝑛 процедур голосования);
- корректность подписи Регистратора на всех бюллетенях (с помощью функции 𝐵𝑆.`Verify`);
- корректность подписи Избирателя на всех бюллетенях (с помощью функции 𝑆.`Verify`);
- уникальность транзакции с указанным ключом проверки подписи;
- доказательства корректности содержимого бюллетеней (с помощью функции 𝑆𝐸.`VerifyEnc`);
- осуществляет гомоморфное сложение успешно проверенных бюллетеней (с помощью функции 𝑆𝐸.`Add`);
- проверяет доказательства корректности частичного расшифрования (с помощью функции 𝑆𝐸.`VerifyDecPart`);
- осуществляет агрегирование результатов расшифрования (с помощью функции 𝑆𝐸.`DecAgg`) и сравнивает полученное значение с опубликованным.

### 4.7. Публикация результатов

В случае успешного аудита Наблюдатель информирует Организатора о своем согласии с итогами. После этого Организатор для каждого 𝑖 ∈ {1, …, 𝑛} получает из Учетчика значение `resultᵢ` и формирует итоги голосования.

## 5. Совместимость с предыдущими версиями протокола

### 5.1. Возможность изменения протокола подписи вслепую

Протокол тайного голосования предусматривает изменение протокола использования подписи вслепую с протокола TeZhu 2022 на протокол на основе RSA установкой соответствующих системных параметров.

В этом случае протокол формирования и проверки подписи вслепую задается следующими алгоритмами:

- `KeyGen(k) → (sk, pk)` — алгоритм генерации ключей, принимающий на вход параметр безопасности 𝑘 и возвращающий пару ключей (𝑠𝑘, 𝑝𝑘), где 𝑠𝑘 — ключ подписи, 𝑝𝑘 — ключ проверки подписи;
- ⟨`Sign(sk)`, `User(pk, m)`⟩ → (𝑏, 𝜎) — интерактивный протокол, выполняемый между подписывающим, который обладает ключом подписи 𝑠𝑘, и клиентом, который обладает сообщением 𝑚; подписывающий выдает 𝑏 = 1, если взаимодействие успешно завершилось, и 𝑏 = 0 в противном случае; клиент выдает значение подписи 𝜎 в случае успешного завершения протокола и код ошибки в противном случае;
- `Verify(pk, m, σ) → b` — детерминированный алгоритм проверки подписи, принимающий на вход ключ проверки подписи 𝑝𝑘, сообщение 𝑚 и подпись 𝜎 и возвращающий единицу, если значение подписи верное, и ноль в противном случае.

В качестве протокола формирования и проверки подписи вслепую используется схема подписи вслепую на основе RSA, предложенная в работе [5] (см. п. 5.1.1), при этом для хэширования сообщения используется конструкция FDH, определенная в п. 5.1.2.
